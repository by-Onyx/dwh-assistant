# Ассистент по проектированию DWH — задания 1 и 2

Учебный помощник для сбора требований и подготовки предварительных моделей DWH в разных отраслях. Задание 1 — консольный агент с потоком и ручными вызовами функций. Задание 2 — Notebook на LangChain с отдельной файловой памятью фактов, которая сохраняется после перезапуска.

**Все локальные модели — до 4B.** Основная: Qwen3-4B-Instruct-2507 Q4_K_M. Для сравнения: Qwen2.5-3B и Qwen2.5-1.5B Instruct Q4_K_M. Проект выполнен по домашнему заданию 04 с приемами prompt engineering из 03.

**Пример работы агента находится здесь: [запрос и ответ про автосалон](examples/car_dealership.md).** В файле приведены исходный запрос и фактический ответ Qwen3-4B без ручных правок.

## Задание 2: LangChain и память фактов

**Откройте [Notebook с кодом и выполненной демонстрацией](02_langchain_fact_memory.ipynb).**

В этой ветке добавлен DWH-чат на LangChain. Он извлекает ключевые факты отдельным LLM-вызовом, записывает их в `memory.json` и восстанавливает после перезапуска. В памяти — имя, стек, уровень, цель и сведения о DWH-проекте; история сообщений туда не записывается. Служебные события выводятся в отдельной CELL, основной чат содержит только сообщения пользователя и ответы агента.

Материалы для сдачи:

- [Notebook](02_langchain_fact_memory.ipynb) — запуск чата, отдельная служебная CELL и два независимых процесса в демонстрации.
- [Файл памяти с вымышленным профилем](examples/memory.json).
- [Реальная демонстрация перезапуска в JSON](evidence/memory_restart.json).
- [Отчет по заданию 2](reports/homework_2.md).

### Установка и запуск Notebook в Windows

Откройте PowerShell в корне этого репозитория. Команды не требуют активации окружения:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m ipykernel install --prefix .venv --name dwh-assistant --display-name "Python (DWH assistant)"
powershell -NoProfile -ExecutionPolicy Bypass -File .\setup.ps1
.\.venv\Scripts\python.exe -m notebook 02_langchain_fact_memory.ipynb
```

В меню Notebook выберите ядро **Python (DWH assistant)**. Выполните ячейки импорта, служебной CELL, конфигурации и чата по порядку. В конфигурации оставьте `BACKEND = "local-4b"`; укажите свой `USER_ID`. Модель по умолчанию — Qwen3-4B; варианты 1.5B и 3B сохранены.

Если модели уже скачаны в другой папке с `models/` и `runtime/`, повторная загрузка не нужна. Перед запуском Jupyter укажите эту папку:

```powershell
$env:DWH_ASSETS_DIR = 'D:\папка-с-моделями-и-runtime'
.\.venv\Scripts\python.exe -m notebook 02_langchain_fact_memory.ipynb
```

Или измените `ASSETS_DIR` в Notebook. Для CPU поставьте `CPU = True`. Если сервер уже запущен отдельно, поставьте `START_LOCAL_SERVER = False`: Notebook подключится по адресу из `config.json`. При занятом порте новый собственный сервер не запускается.

### Проверить память вручную

1. Напишите: «Меня зовут Алексей. Мой стек — Python и PostgreSQL. Мой уровень — начинающий аналитик. Моя цель — спроектировать DWH для автосалона».
2. В служебной CELL проверьте `memory_saved`; `/memory` показывает сохранённые факты в этой же CELL.
3. Отправьте `/exit`, чтобы остановить принадлежащий Notebook сервер. Затем перезапустите ядро (Restart Kernel) либо закройте и вновь откройте Jupyter.
4. Выполните ячейки запуска с прежними `USER_ID` и `MEMORY_PATH`.
5. Спросите: «Как меня зовут и какой у меня стек? Продолжим знакомство». Агент получает профиль из файла и продолжает с незаполненного поля.

Команды: `/forget stack` удаляет одно поле; `/clear` очищает только текущий профиль; `/exit` завершает чат с сохранением памяти. Явное исправление, например «Мой стек теперь — Python и ClickHouse», заменяет поле. Для неоднозначных дополнений лучше сообщать полное новое значение.

Рабочий `memory.json` и его lock/tmp-файлы исключены из Git. Профили разделяются `user_id`; это идентификатор в учебном приложении, не система аутентификации. В Git включён только вымышленный пример `examples/memory.json` и журнал его демонстрации.

### Реализация

Используется `langchain-core` — основной пакет LangChain с LCEL-цепочками. Первая цепочка: `ChatPromptTemplate | RunnableLambda(LLM) | JSON/Pydantic validation`. Вторая: `ChatPromptTemplate | RunnableLambda(LLM) | StrOutputParser`. Локальный LLM вызывается через общий клиент проекта; отдельная внешняя модель для извлечения не нужна.

`FileFactMemory.load_memory_variables()` читает факты; `save_context()` проверяет подтверждающую цитату и атомарно обновляет профиль. Файловая блокировка предотвращает потерю обновлений разных профилей. Поврежденный файл не сбрасывается молча. Невалидное извлечение повторяется один раз; затем прежняя память сохраняется, а ошибка выводится в служебную CELL. Если ответ модели оборвётся после записи фактов, уже сохранённые факты остаются на диске.

Подсказки задания `ConversationChain`/`BaseChatMemory` не являются обязательным API. Использован современный LCEL с собственным адаптером фактов; буфер истории `RunnableWithMessageHistory` здесь не нужен. Схема JSON проверяется кодом; нативный tool calling для извлечения не используется.

Ограничения: цитата подтверждает происхождение текста, но не его семантическую классификацию. Модель может пропустить факт или ошибиться в ответе по DWH. Содержимое профиля можно проверить и изменить. Между перезапусками доступны только сохраненные факты, а не вся предыдущая переписка. Стек/цели сохраняются строками; изменения заменяют полное поле.

## Требования

- Windows 10/11, Python 3.12 или новее; в исходной среде проверен Python 3.12.3.
- Интернет для первой загрузки llama.cpp и моделей, около 6 ГБ свободного места для моделей плюс сервер.
- Для GPU используется Vulkan. Тестовая среда: RTX 3060 Ti, 64 ГБ RAM. Доступен запуск на CPU.
- Для консольного задания 1 используется стандартная библиотека. Для Notebook задания 2 нужны зависимости из `requirements.txt`.

## Быстрый запуск из новой копии проекта

1. Скачайте репозиторий или распакуйте архив. Откройте PowerShell в папке, где находится README.md.
2. Проверьте Python:

```powershell
python --version
```

3. Установите локальный сервер и три модели:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\setup.ps1
```

Скрипт скачивает Windows Vulkan-сборку llama.cpp b11524, затем модели из закрепленных ревизий. SHA-256 моделей сверяется с model_manifest.json. Модели и сервер не включены в Git. Если загрузка прервана, повторите ту же команду.

4. Запустите ассистента:

```powershell
python run_local.py --backend local-4b
```

Launcher запускает свой сервер на 127.0.0.1, ожидает готовности, открывает чат и завершает сервер после выхода. При проблемах с Vulkan:

```powershell
python run_local.py --backend local-4b --cpu
```

5. Введите запрос. Для нескольких строк введите `/paste`, вставьте текст и завершите отдельной строкой `/end`. Команда `/reset` очищает историю, `/exit` завершает чат. Ctrl+C и EOF также завершают работу.

История хранится в памяти сеанса. Журнал JSONL записывается в logs/; он не восстанавливает историю автоматически. Контекст сервера — 8192 токена; длинные проекты лучше разбивать на этапы и новые сеансы. Незавершенный ход при ошибке откатывается.

Помоги спроектировать DWH для автосалона. Есть CRM с обращениями и этапами

## OpenRouter

Облачный профиль в config.json: liquid/lfm-2.5-2.6b:free. Ключ задается только в окружении терминала:

```powershell
$env:OPENROUTER_API_KEY = 'ваш-ключ'
python assistant.py --backend openrouter
```

Ключ не записывается в исходники и журналы. После работы можно удалить переменную:

```powershell
Remove-Item Env:OPENROUTER_API_KEY
```

Текущий профиль 2.6B не проверен: последняя попытка с использовавшимся ключом вернула HTTP 401. Исторический успешный прогон другого облачного профиля сохранен в отчете по заданию. Доступность и стоимость определяются провайдером. Для сохранения ограничения до 4B выбирайте модели не больше этого размера; переопределение --model/OPENROUTER_MODEL кодом не ограничено.

## Как работает агент

1. Модель выбирает действие и печатает `<call>{"name":"rules","arguments":{"topic":"modeling"}}</call>` обычным текстом.
2. Python проверяет JSON, имя функции и аргументы, выполняет разрешенную функцию и возвращает observation.
3. Модель формирует ответ по требованиям. При моделировании выполняется еще один независимый проход той же модели по более строгой памятке, после которого финал выводится потоком.

Три функции:

| Функция | Назначение |
|---|---|
| catalog(table) | Учебные orders/order_items/customers/products; общий режим использует каталог только по явному запросу |
| rules(topic) | Памятки requirements/modeling/inventory/etl/grain/scd2/layers/quality |
| check_design(design) | Проверка заполненности grain/facts/dimensions и дубликатов списков |

Нативные function calling, tools calling и MCP не используются. Система не подключается к реальным БД и не выполняет SQL. check_design проверяет структуру макета, а не бизнес-смысл.

## Проверки и ограничения

```powershell
python -m unittest -v
python run_local.py --backend local-4b --evaluate-general
python run_local.py --backend local-1.5b --evaluate
python run_local.py --backend local-3b --evaluate
```

Unit-тесты не требуют моделей и сети. evaluate-general проверяет два шага диалога об аптеке, логистику и университет. Старый evaluate сравнивает baseline/improved на десяти учебных сценариях каждой локальной модели. Новые журналы пишутся в logs/ и исключены из Git; сохраненные доказательства исходных запусков находятся в evidence/logs/.

**Модель ошибается в гранулярности, формулах и бизнес-правилах.** Повторный проход не гарантирует исправления. Метрики завершения и правильного выбора функции не означают правильный DWH-проект. Нужна проверка архитектором; реальные ограничения перечислены в reports/general_mode.md. Пример автосалона намеренно сохранен с ошибками и без ручных правок.

При ошибках загрузки проверяйте сеть и свободное место; при ошибках сервера — logs/server_*.log и --cpu. HTTP 401 в OpenRouter означает проблему доступа/ключа. Увеличение --max-tokens может помочь при обрыве длинного ответа, но не исправляет его смысл.
