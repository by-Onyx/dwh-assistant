# Домашнее задание: исходный учебный прогон

Этот отчет фиксирует первоначальные результаты practicum. Текущий общий режим, модели до 4B и ограничения описаны в general_mode.md; запуск — ../README.md.

Выполнено 9 октября 2026 года по 04_Домашнее_задание.html с использованием
материалов 03_promt_eng.html. Тема: помощь архитектору хранилища данных.

Реализован и запущен консольный ассистент: две локальные модели, история,
стриминг и ручной разбор вызовов функций из текста ответа.
OpenRouter проверен реальными запросами после предоставления ключа:
аутентификация HTTP 200, SSE-ответы и вызовы функций работают. Ключ не сохранен.

## Ассистент и инструменты

Ассистент уточняет требования, помогает выбирать гранулярность,
проектировать витрину продаж, историю измерений и проверки качества.

* catalog(table): фиксированный каталог orders, order_items, customers, products.
* rules(topic): фиксированные памятки grain, scd2, layers, quality.
* check_design(design): заполненность grain/facts/dimensions и дубликаты списков.
  Проверка не подтверждает бизнес-смысл, SQL и реальные данные.

Модель пишет, например:
<call>{"name":"catalog","arguments":{"table":"order_items"}}</call>.

Код разбирает обычное поле content, проверяет JSON и allowlist, выполняет
заданную функцию, пишет результат в лог. В payload отсутствуют tools,
tool_choice, function_call; приложение не использует MCP.
Доступа к реальным БД и выполнения SQL нет. Источники — учебные константы.

## Промпт-инжиниринг по материалам 03

Базовый вариант: роль, функции, минимальное описание формата.

Первые улучшения показали ошибки малых моделей: копирование перечня вариантов
в один аргумент, незакрытые блоки, самостоятельное придумывание Observation.
Эти прогоны сохранены, а не выданы за успешные.

Итоговая версия:
1. Одна функция на шаг, конкретные схемы аргументов без неоднозначных списков.
2. Пять few-shot примеров отдельными сообщениями user/assistant.
3. Разбор формата и аргументов выполняется кодом.
4. Стоп-маркеры на границах диалога ограничивают продолжение примера.
5. После вызова — отдельный короткий промпт ответа по типу задачи.
   Он получает текущий вопрос и observation без учебных диалогов.
6. Ошибка функции возвращается точно из результата, без пересказа LLM.
7. Два исправления формата, ограничение шагов и повторных вызовов.

Использованы role prompting, few-shot, output structuring, delimiters,
decomposition, prompt chaining и цикл действие → наблюдение → ответ.
Внешнего RAG, self-consistency и требования печатать скрытые рассуждения нет.
Результат относится к сочетанию промптов и цепочки, а не изолированной
проверке одной фразы. Промпты промежуточных версий — improved_v1/v2/v3.txt.

## Итоговое сравнение

temperature=0.1, seed=42, max_tokens=650; новая история для каждого сценария.
Сценарии: orders, order_items, отсутствующая payments, SCD2, слои, качество,
некорректный и корректный макеты, проект витрины, неизвестные требования.

| Модель | Вариант | Завершенные ответы | Верное действие/аргументы | Ожидаемые термины |
|---|---|---:|---:|---:|
| local-1.5b | baseline | 6/10 | 5/10 | 5/10 |
| local-1.5b | improved | 10/10 | 10/10 | 8/10 |
| local-3b | baseline | 8/10 | 3/10 | 3/10 |
| local-3b | improved | 10/10 | 10/10 | 10/10 |
| openrouter | improved | 10/10 | 9/10 | 9/10 |

tool_ok проверяет имя и точные аргументы; для запроса без инструмента —
отсутствие вызовов. keyword_ok — эвристика по словам, не экспертная оценка.
Сценарии использовались при настройке; это не независимый набор оценки.

В improved обе модели выбрали верное действие в 10/10 сценариев.
3B прошла проверку терминов в 10/10, 1.5B — в 8/10.
Для локальной работы выбран профиль local-3b. Облачная модель:
apodex/apodex-1.1-mini:free, reasoning.effort=none, reasoning.exclude=true.
После отключения необязательных рассуждений ограничение max_tokens=650
позволило получить завершенные ответы. В облаке — 10/10 завершений,
9/10 верных действий и 9/10 проверок терминов. Стоимость по usage.cost — 0.
Первый неудачный запрос с прежними настройками сохранен в логах.

Ограничения по ручному просмотру:
* 1.5B в вопросе качества переводит quantity/unit_price на русский, поэтому
  часть keyword-проверки не проходит; пункт о NULL остается слишком кратким.
* 1.5B при неизвестных требованиях просит уточнить данные, но не дает
  полного перечня вопросов о гранулярности.
* 3B в ответе о SCD2 пропускает часть условий о границах интервалов
  и источнике истории, хотя они есть в памятке инструмента.
* Облачная модель в сценарии проектирования витрины выбрала check_design
  вместо catalog(all), поэтому ответила о проверке макета. Это зафиксированный
  провал, не успешный проект. Остальные девять сценариев прошли проверки.
* Десять сценариев не доказывают надежность на произвольных проектах.

## Пример полученного проекта

Итоговый ответ 3B предложил:
* одна позиция заказа; составной ключ (order_id,line_no);
* quantity и revenue = quantity * unit_price;
* измерения customer, product, date из order_date;
* order_items → orders по order_id, → products по product_id;
  orders → customers по customer_id;
* историю customers/SCD2 для сегмента на дату продажи;
  уточнение отмен, возвратов, валюты и SLA.

Это проект по учебному каталогу. Бизнес-правила возвратов и отмен пока
неизвестны, поэтому они не включены в формулу выручки.

## Запуск и сдача

Из папки проекта:

    python run_local.py --backend local-3b --mode practicum

Смена модели: --backend local-1.5b; повтор сравнения: добавьте --evaluate.
Подробности установки и OpenRouter — в ../README.md.

dwh-assistant-git.zip содержит код, промпты, инструкцию,
отчет, манифест моделей и реальные логи.
Модели и бинарная среда остаются локально; в архив не включены из-за размера.
setup.ps1 скачивает закрепленные версии и проверяет SHA-256.

Пункт подключения к OpenRouter выполнен и проверен. Для новых запусков задайте
OPENROUTER_API_KEY в окружении и выполните assistant.py --backend openrouter.
Постоянное хранение ключа не настроено; в исходниках, логах и архиве ключа нет.
Модель по умолчанию указана в config.json.
