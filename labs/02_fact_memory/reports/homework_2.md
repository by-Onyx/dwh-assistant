# Задание 2: LangChain-чат с памятью фактов

Реализовано в ветке `lang-chain`. Финальная проверка: 20 октября 2026 года. Тема сохранена: помощник по проектированию DWH; основная модель Qwen3-4B-Instruct-2507 Q4_K_M. Все локальные модели не больше 4B.

## Соответствие заданию

| Требование | Реализация |
|---|---|
| Чат на LangChain / chain | Две настоящие LCEL RunnableSequence: извлечение и ответ, langchain-core 1.6.12 |
| Извлечение ключевых фактов | Отдельный LLM-вызов, JSON с key/value/evidence, Pydantic и проверка точной цитаты |
| Память — отдельные факты | FileFactMemory; в JSON только version/profiles/facts, без списка сообщений |
| Запись и чтение при запуске | UTF-8 JSON, атомарная замена, файловая блокировка, валидация существующего файла |
| Работа после перезапуска | Демонстрация в двух отдельных процессах, второй читает уже записанный файл |
| Несколько профилей | user_id; очистка/удаление касается только выбранного профиля |
| Служебная информация в своей CELL | NotebookChat.service_output отдельно от chat_output; также отдельная статическая CELL проверки |
| Notebook, память, демонстрация | [Notebook](../notebooks/02_fact_memory.ipynb), [memory.json](../examples/memory.json), [результат](../evidence/memory_restart.json) |

В задании ConversationChain/BaseChatMemory перечислены в подсказках. Реализация использует современный LCEL и собственный адаптер с load_memory_variables()/save_context(), без буфера истории. Ключевые компоненты LangChain выполняются реально: это не имитация chain на словарях. [RunnableSequence в справочнике LangChain](https://reference.langchain.com/python/langchain-core/runnables/base/RunnableSequence).

## Реальная демонстрация

Сведения учебные, не личные данные автора. Запуск A и B используют одну локальную модель; LLM-процесс сервера может оставаться запущенным, но процессы приложения независимы. Между ними передаются только путь файла и user_id, а история или объект памяти не передаются.

PID первого процесса: **26896**, второго: **6320**.

Первое сообщение:

> Меня зовут Алексей. Мой стек — Python и PostgreSQL. Мой уровень — начинающий аналитик. Моя цель — спроектировать DWH для автосалона. Предметная область — автосалон.

Ответ первого процесса (без правок):

> Какие источники данных доступны?

После завершения первого процесса второй получил вопрос:

> Как меня зовут, какой у меня стек и какая цель? Затем задай следующий вопрос анкеты.

Ответ второго процесса (без правок):

> Вас зовут Алексей, ваш стек — Python и PostgreSQL, ваша цель — спроектировать DWH для автосалона.  
> 
> Следующий вопрос анкеты: Какие источники данных доступны?

Восстановлены имя, стек, уровень, цель и отрасль. Следующий вопрос — об источниках, на него ранее ответа не было. Вопрос о профиле не добавил новых фактов и не изменил сохраненные.

Все семь автоматических проверок демонстрации прошли: разные PID; первый профиль пуст; факты извлечены; второй процесс загрузил тот же профиль; вопрос не изменил память; ответ упоминает сохраненные данные; оба извлечения прошли проверку.

## Проверки

- **27 unit-тестов прошли**: 13 исходных и 14 для памяти/цепочек/вывода. Проверены изоляция профилей, исправление и удаление фактов, поврежденный JSON, дублирующиеся ключи, неподтвержденные значения, атомарность записи при ошибке диска, конкурирующие записи, сохранение фактов при ошибке ответа и раздельные output-блоки.
- **Notebook выполнен через nbclient целиком**: 7 кодовых ячеек, без error outputs. Реальные ответы и проверки сохранены в Notebook.
- Прежний CLI после рефакторинга запущен с локальной 4B. Запрос полей учебной products завершился с кодом 0, функция catalog выполнена, поток получен. Это регрессионная проверка транспорта/цикла, не подтверждение правильности всех утверждений модели. [Журнал](../evidence/logs/refactor_cli_smoke.log).
- Версии прямых зависимостей — requirements.txt; полный снимок проверенного Windows/Python 3.12-окружения — requirements-lock.txt. Для установки точного снимка можно использовать `pip install -r requirements-lock.txt` в новом venv.

В первом реальном прогоне модель пыталась переносить старые факты в ответ извлекателя, хотя последнее сообщение было вопросом. Валидация цитат отвергла обновление, память не пострадала; начальный неуспешный результат сохранен в memory_restart_initial.json. Затем старый профиль исключен из входа извлекателя, добавлены few-shot примеры вопросов без новых фактов и регрессионный тест. Текущий успешный результат — memory_restart.json.

## Рефакторинг

Из assistant.py выделены общий SSE-клиент, ручной протокол, журнал и корневой путь проекта. Для прежних импортеров сохранены Client/EventLog/parse_response/ROOT. Локальный сервер перенесен в контекстный менеджер LocalServer: один жизненный цикл используется CLI, Notebook и демонстрацией; порты и alias берутся из config.json. Добавлен assets_dir для повторного использования скачанных моделей.

Новые компоненты разделены по ответственности: fact_memory.py — файл и валидация; fact_agent.py — LangChain; notebook_ui.py — вывод. Первый учебный режим и его тесты сохранены. Реальные примеры первоначального проекта, включая ответ про автосалон, не переписывались.

## Практические ограничения

Проверка цитаты доказывает присутствие текста в последнем сообщении, но не правильность смыслового выбора поля. Модель может пропустить факт; при невалидном JSON действующая память сохраняется. При ответе по DWH возможны ошибки. Между перезапусками сохраняются только факты, а не произвольный контекст переписки.

Stack/goals — строки; новое полное значение заменяет старое. Для неоднозначных дополнений следует сообщить полный актуальный стек/цель. user_id разделяет профили, но не выполняет аутентификацию. Рабочая память исключена из Git; включенный пример вымышленный.

Основные команды запуска и ручная проверка после Restart Kernel — в [README](../README.md).
